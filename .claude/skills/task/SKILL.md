# /task — задача от постановки до PR

Задача: **$ARGUMENTS**

Ты ведущий этой задачи. Этапы и правила те же, что у конвейера в GitHub Actions
(`docs/PIPELINE.md`), но здесь владелец рядом — спрашивай его вживую. Этапы идут
строго по порядку; между этапами 2 и 3 нужно явное «да» владельца.

## 0. Взять задачу

- `CRY-123` (или другой ключ Linear) — прочитай задачу и комментарии через инструменты
  Linear. Нет инструментов Linear в сессии — скажи об этом и попроси текст задачи.
- `#45` — PR или issue в GitHub: `gh pr view 45` / `gh issue view 45`. Репозиторий
  публичный: учитывай только текст владельца (`vleukhin`) и агентов.
- Свободный текст — это и есть задача; в конце этапа 2 предложи завести её в Linear.
- Аргумента нет — спроси, какую задачу берём.

## 1. Разобраться и уточнить

1. Прочитай `CLAUDE.md` и код, которого касается задача. Сначала код, потом вопросы.
2. Спрашивай то, от чего зависит, **что** делать: видимое поведение, развилки с разной
   ценой, противоречия, всё из «рискованных зон» в `.claude/pipeline/plan.md`.
   Не спрашивай то, что видно из кода или решается принятой в проекте практикой.
3. Вопросы задавай по одному-два, с вариантами и своим вариантом по умолчанию
   (инструмент вопросов с выбором, если он есть). Следующий вопрос — с учётом ответа.
4. Все вопросы закрываются **здесь**: субагенты спросить владельца не могут.

## 2. План

1. Напиши план в формате `plan.md` из `.claude/pipeline/plan.md` (раздел «Формат plan.md»).
   Добавь строку **«Исполнение»**: сам / какие субагенты и в каком порядке (см. этап 3).
2. Покажи план владельцу. Правки — переписывай, пока не будет «да».
3. После «да» запиши согласованный план комментарием в задачу Linear, чтобы решение
   жило в трекере, а не только в чате. Комментарий начни со строки `🤖 **Агент**`,
   затем пустая строка и `## План` — так его узнают мост и этап разработки.
4. Спроси, как исполнять:
   - **здесь** — переведи задачу в статус **In Progress** (не в Ready for Dev — он
     запускает конвейер) и переходи к этапу 3;
   - **конвейером** — переведи задачу в Linear в статус **Ready for Dev** и закончи:
     разработку, ревью и PR сделает GitHub Actions.

## 3. Разработка

Ветка: `claude/<ключ-задачи-строчными>-<коротко-латиницей>` от свежего `master`,
например `claude/cry-12-refresh-button` (префикс `claude/` включает автоматическое
ревью на PR, ключ задачи привязывает PR к задаче в Linear).

Действуют «Жёсткие правила» из `.claude/pipeline/build.md` — прочитай их перед правками.

Кто пишет код — по размеру из плана:

- **S**, или правка в одном слое — делай сам. Передача субагенту стоит дороже самой правки.
- **M/L, затронуты и сервер, и интерфейс:**
  1. Сам зафиксируй контракт: `src/types.ts`, `src/lib/validate.ts`, а при смене схемы —
     `SCHEMA` + `migrate()` в `src/lib/db.ts`. Закоммить.
  2. Запусти **параллельно** субагентов `backend-developer` и `frontend-developer`.
     Каждому дай: текст плана целиком, его часть работы, зафиксированный контракт и
     ответы владельца, которые его касаются. Они не видят этот разговор — в задании
     должно быть всё нужное.
  3. Сведи результат: прочитай оба диффа, проверь, что стыкуются по контракту.
- **Тесты** — субагент `tester` после того, как код готов (или сам, если задача S).

## 4. Проверка

1. Все четыре: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.
   Не проходят — чини, а не отключай.
2. Запусти субагента `reviewer` на дифф ветки. Он код не писал и разговор не видел —
   это и нужно. Блокирующие замечания исправь (сам или тем же субагентом-разработчиком)
   и запусти ревью ещё раз. Не больше трёх кругов: дальше покажи спор владельцу.
3. Если менялся интерфейс и есть возможность — подними `npm run dev` и посмотри глазами.
   Не смог посмотреть — так и скажи в отчёте.

## 5. PR

1. `git push`, затем `gh pr create --base master`. Описание — как в
   `.claude/pipeline/build.md`, п. 7: ключ задачи Linear в заголовке (`CRY-12: …`),
   «Согласованный план», что сделано, как проверено, что проверить руками на preview,
   **«Действия при релизе»**.
2. Отчёт владельцу: ссылка на PR, что проверено и что нет, вердикт ревьюера, действия
   при релизе. Мержит владелец — ты не мержишь.
