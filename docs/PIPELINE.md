# Конвейер агентов

Задача ставится в Linear, дальше её ведут агенты Claude Code в GitHub Actions.
GitHub Issues не используются: Linear и GitHub связывает свой мост (`vleukhin/agent-bridge`).
Ваши точки контроля — две: согласовать план и смержить PR.

```
Linear: задача в проекте Depo + метка agent:plan
  │  вебхук
  ▼
agent-bridge (Vercel)   проверяет подпись, по проекту находит репозиторий,
  │  workflow_dispatch  запускает нужный воркфлоу
  ▼
GitHub Actions
  └─ 1. План        агент читает код; если неясно — вопросы в Linear       код не меняется
                    (метка agent:questions); ваш ответ комментарием
                    перезапускает планирование; затем план
        ↓ вы: метка agent:build   (или замечания + метка agent:plan)
  └─ 2. Разработка  ветка claude/cry-12-…, код, тесты, PR; ссылка — в Linear
        ↓ автоматически
  └─ 3. Проверки    CI (lint, typecheck, test, build) + ревью отдельным агентом
                    + preview-деплой Vercel
        ↓ вы: смотрите PR и preview, мержите   (или «@claude поправь …» в PR)
  └─ 4. Релиз       Vercel выкатывает master → smoke-проверка прода
```

## Как пользоваться

1. В Linear: новая задача **в проекте Depo** + метка `agent:plan`. Проект обязателен —
   по нему мост понимает, в какой репозиторий идти. Через пару минут в задаче
   появится комментарий агента.
2. Если агенту чего-то не хватает, придёт «Вопросы по задаче» с вариантами и ответом
   по умолчанию, а на задаче появится метка `agent:questions`. Ответьте комментарием —
   хоть «1а, 2б», хоть «всё по умолчанию»; планирование запустится само. Кругов
   вопросов не больше двух, дальше агент пишет план и перечисляет свои допущения.
3. Прочитайте план. Согласны — поставьте метку **`agent:build`**. Не согласны —
   напишите замечания комментарием и поставьте `agent:plan` ещё раз.
4. Агент откроет PR и пришлёт ссылку в задачу. Linear сам привяжет PR к задаче
   (по ключу `CRY-12` в названии ветки и заголовке). В PR: описание, результат CI,
   комментарий «Ревью агента» с вердиктом и списком «что проверить руками».
5. Нужны правки — комментарий **в PR на GitHub**: `@claude поправь замечания ревью`.
6. Всё хорошо — **Merge**. Это и есть согласование релиза: Vercel выкатит прод,
   `smoke.yml` проверит, что он отвечает. Блок «Действия при релизе» в PR
   (переменные окружения, миграции) выполните до мержа.

Метки `agent:plan` и `agent:build` — это команды: воркфлоу снимает метку, когда берёт
задачу, поэтому повторить этап — значит поставить метку ещё раз. Комментарии агентов
начинаются с 🤖: они пишутся вашим же API-ключом, и по этому значку мост отличает их
от ваших (иначе ответ агента сам запускал бы следующий круг).

## Интерактивный режим: `/task`

Для задач, где требования неясны и нужен живой диалог. В сессии Claude Code
(локально, в вебе или с телефона) в этом репозитории:

```
/task CRY-123        задача из Linear
/task #45            PR или issue в GitHub
/task <текст>        задача прямо из сообщения
```

Команда (`.claude/skills/task/SKILL.md`) ведёт те же этапы, что и конвейер:
вопросы вживую → план → ваше «да» → разработка → проверка → PR. Согласованный план
записывается комментарием в задачу. После плана можно не продолжать в сессии, а
отдать исполнение конвейеру: команда поставит метку `agent:build`.

### Субагенты

Лежат в `.claude/agents/` и поэтому работают одинаково локально и в облачных сессиях
(личные субагенты из `~/.claude/agents/` есть только на вашем компьютере).

| Субагент | Зона | Когда вызывается |
| --- | --- | --- |
| `backend-developer` | `src/lib/`, `src/app/api/` | задачи M/L, где затронуты и сервер, и интерфейс |
| `frontend-developer` | `src/features/`, `src/components/`, `src/hooks/`, страницы | то же, параллельно с backend |
| `tester` | `src/lib/__tests__/` | после разработки |
| `reviewer` | только чтение | перед PR; код не писал и разговор не видел |

Как это устроено и почему:

- **Маленькие задачи ведущий делает сам.** Субагент начинает с пустого контекста,
  и передать ему задачу на три строки дороже, чем эти три строки написать.
- **Перед параллельной работой ведущий фиксирует контракт** (`src/types.ts`,
  `src/lib/validate.ts`, схема БД). Иначе backend и frontend разойдутся в форме данных.
- **Все вопросы владельцу задаются до делегирования.** Субагенты спросить вас не
  могут — если им не хватает решения, они возвращают вопрос ведущему.
- **Зоны не пересекаются**, поэтому два разработчика правят одну рабочую копию без
  конфликтов.

В конвейере GitHub Actions этап разработки пока идёт одним агентом, без субагентов.

Вызвать субагента вне `/task` можно напрямую: «пусть reviewer посмотрит ветку» или
`@agent-reviewer`.

## Разовая настройка

### 1. Мост (`vleukhin/agent-bridge`)

Пошагово — в README моста. Коротко: задеплоить на Vercel, задать три переменные
(`LINEAR_WEBHOOK_SECRET`, `LINEAR_API_KEY`, `GITHUB_DISPATCH_TOKEN`), создать в Linear
вебхук на `https://<домен-моста>/api/linear` с событиями Issues и Comments.

### 2. Этот репозиторий

1. **Установить приложение Claude**: https://github.com/apps/claude → Install → только
   `vleukhin/depo`. От его имени агент пушит ветку и открывает PR.
2. **Секреты** в Settings → Secrets and variables → Actions:
   - `CLAUDE_CODE_OAUTH_TOKEN` (подписка Claude: `claude setup-token`) **или**
     `ANTHROPIC_API_KEY` (оплата по токенам) — один из двух;
   - `LINEAR_API_KEY` — личный ключ Linear: воркфлоу читает им задачу и пишет
     комментарии. Публикует результат отдельное задание из чистой копии `master`,
     после старта агента ключ в его задании не используется.
3. **Защитить `master` — обязательно**: Settings → Branches → Require a pull request
   before merging + Require status checks (`check`), без исключения для администраторов.
   На этапе разработки агент выполняет код проекта (тесты, сборку) с токеном, у которого
   есть право записи в репозиторий; список разрешённых команд — не граница
   безопасности, граница — защита ветки.
4. **Выключить GitHub Issues Sync** для этого репозитория в Linear (Settings →
   Integrations → GitHub), если включали: он больше не нужен. Сама интеграция Linear
   с GitHub пусть остаётся — она привязывает PR к задачам и двигает статусы.
5. **Развести окружения Vercel — до первой задачи.** См. следующий раздел.

### 3. Linear

Метки `agent:plan`, `agent:questions`, `agent:build` уже созданы на уровне рабочего
пространства. У задачи должен быть проект, для которого в мосте есть маршрут.

### Что проверить на первой задаче

Воркфлоу и мост не запускались вживую до первой настоящей задачи. Если что-то не
сработало, смотреть по цепочке:

- **Vercel → проект моста → Logs.** Запрос пришёл? `401` — не совпал секрет вебхука;
  `skipped` в ответе — событие не распознано как триггер.
- **Комментарий 🤖 «Мост» в задаче** — мост сам пишет, если не нашёл маршрут или
  GitHub отказал в запуске (обычно токен без права Actions или не тот репозиторий).
- **GitHub → Actions** — запуск «Агент · 1 · План» появился? Упал на шаге «Взять
  задачу из Linear» — проверьте секрет `LINEAR_API_KEY`.

Кто может запускать агентов: участники вашего рабочего пространства Linear (вебхук
подписан его секретом) и те, у кого есть право записи в репозиторий (ручной запуск
воркфлоу). Пока вы там один — это только вы.

## Репозиторий публичный — задачи тоже становятся публичными

Согласованный план копируется в описание PR, а логи GitHub Actions в публичном
репозитории видны всем. Всё, что вы написали в задаче Linear и в ответах агенту,
может оказаться на виду. Либо не пишите в задачах ничего чувствительного (адреса,
суммы, имена, внутренние схемы), либо сделайте репозиторий приватным — для приложения,
которое управляет выводом средств, второе надёжнее.

## Preview-деплои и боевые секреты

По `DEPLOY.md` переменные окружения заданы со scope **Production + Preview**. Значит,
код из ветки агента разворачивается в preview с боевой базой Turso и ключом Bitget с
правом вывода — ещё до того, как вы его посмотрели. Для конвейера это нужно исправить:

- в Vercel → Settings → Environment Variables оставьте боевые значения только для
  **Production**;
- для **Preview** задайте отдельные: свою `APP_PASSWORD`/`AUTH_SECRET`, отдельную
  базу Turso (`turso db create depo-preview`, можно с копией данных) и **не задавайте**
  `BITGET_*`, `KUCOIN_*`, `TRONRENTAL_API_KEY`, `EXCHANGE_PROXY_*`, `TELEGRAM_*`,
  `CRON_SECRET`, `EXTERNAL_API_TOKEN`.

Preview при этом остаётся рабочим стендом для ручной проверки интерфейса, но
ошибка в коде агента не дотянется ни до денег, ни до боевых данных.

## Что агентам запрещено

Полный список — в `.claude/pipeline/build.md`. Главное: не мержить и не пушить в
`master`, не ставить npm-пакеты, не трогать `.github/` и `.claude/`, не обращаться к
проду, базе и биржам. В секретах GitHub Actions лежат только токен Claude и ключ Linear — боевых
ключей (биржи, база, пароль приложения) там нет.

## Стоимость и лимиты

Каждый этап — отдельный запуск с лимитом ходов (`--max-turns`) и таймаутом в
воркфлоу. По подписке запуски расходуют её лимиты, по API-ключу — оплачиваются по
токенам. Модель не закреплена (берётся модель по умолчанию у action); закрепить можно
флагом `--model` в `claude_args`.

## Перенос на другие проекты

Скопируйте `.github/workflows/agent-*.yml`, `.github/scripts/linear.mjs`, каталог
`.claude/pipeline/` и напишите свои `CLAUDE.md` и `docs/RUNBOOK.md`. В мосте добавьте
строку в `routes.ts` (проект Linear → репозиторий), а токену `GITHUB_DISPATCH_TOKEN`
дайте доступ к новому репозиторию. В воркфлоу
меняются только команды проверок (`npm run …`) и список `--allowedTools`; в
`.claude/pipeline/*.md` — разделы про рискованные зоны проекта.
