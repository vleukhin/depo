# Конвейер агентов

Задача ставится в Linear (или прямо в GitHub Issues — это одно и то же: команда Linear
синхронизирована с репозиторием), дальше её ведут агенты Claude Code в GitHub Actions.
Ваши точки контроля — две: согласовать план и смержить PR.

```
Issue (шаблон «Задача для агентов», метка agent:plan)
  └─ 1. План        агент читает код; если неясно — задаёт вопросы     код не меняется
                    (метка agent:questions), вы отвечаете комментарием,
                    планирование перезапускается само; затем план
        ↓ вы: метка agent:build   (или замечания + agent:plan заново)
  └─ 2. Разработка  ветка claude/…, код, тесты, PR
        ↓ автоматически
  └─ 3. Проверки    CI (lint, typecheck, test, build) + ревью отдельным агентом
                    + preview-деплой Vercel
        ↓ вы: смотрите PR и preview, мержите   (или «@claude поправь …» в PR)
  └─ 4. Релиз       Vercel выкатывает master → smoke-проверка прода
```

## Как пользоваться

1. **В Linear:** новая задача в команде Crypto Development + метка `agent:plan`.
   **Или в GitHub:** Issues → New issue → «Задача для агентов» (метка ставится сама).
   Через пару минут в задаче появится план.
2. Если агенту чего-то не хватает, вместо плана придёт комментарий «Вопросы по
   задаче» с вариантами и ответом по умолчанию, а на задаче появится метка
   `agent:questions`. Ответьте комментарием — хоть «1а, 2б», хоть «всё по
   умолчанию»; планирование запустится само. Кругов вопросов не больше двух,
   дальше агент пишет план и перечисляет свои допущения.
3. Прочитайте план. Согласны — поставьте метку **`agent:build`**. Не согласны —
   напишите замечания комментарием, снимите и снова поставьте `agent:plan`.
4. Агент откроет PR. В нём: описание, результат CI, комментарий «Ревью агента» с
   вердиктом и списком «что проверить руками», ссылка на preview от Vercel.
5. Нужны правки — комментарий в PR: `@claude поправь замечания ревью` (или что именно).
6. Всё хорошо — **Merge**. Это и есть согласование релиза: Vercel выкатит прод,
   `smoke.yml` проверит, что он отвечает. Блок «Действия при релизе» в PR
   (переменные окружения, миграции) выполните до мержа.

Агентов запускают только ваши действия: воркфлоу проверяют, что метку или
комментарий поставил владелец репозитория (напрямую или через Linear), а в контекст
попадают только ваши комментарии, комментарии из Linear и комментарии самих агентов.

## Интерактивный режим: `/task`

Для задач, где требования неясны и нужен живой диалог. В сессии Claude Code
(локально, в вебе или с телефона) в этом репозитории:

```
/task CRY-123        задача из Linear
/task #45            задача из GitHub Issues
/task <текст>        задача прямо из сообщения
```

Команда (`.claude/skills/task/SKILL.md`) ведёт те же этапы, что и конвейер:
вопросы вживую → план → ваше «да» → разработка → проверка → PR. Согласованный план
записывается комментарием в задачу. После плана можно не продолжать в сессии, а
отдать исполнение конвейеру: команда поставит метку `agent:build`.

### Субагенты

Лежат в `.claude/agents/` и поэтому работают одинаково локально и в облачных сессиях
(личные субагенты из `~/.claude/agents/` есть только на вашем компьютере).

| Субагент | Зона | Когда вызывается |
| --- | --- | --- |
| `backend-developer` | `src/lib/`, `src/app/api/` | задачи M/L, где затронуты и сервер, и интерфейс |
| `frontend-developer` | `src/features/`, `src/components/`, `src/hooks/`, страницы | то же, параллельно с backend |
| `tester` | `src/lib/__tests__/` | после разработки |
| `reviewer` | только чтение | перед PR; код не писал и разговор не видел |

Как это устроено и почему:

- **Маленькие задачи ведущий делает сам.** Субагент начинает с пустого контекста,
  и передать ему задачу на три строки дороже, чем эти три строки написать.
- **Перед параллельной работой ведущий фиксирует контракт** (`src/types.ts`,
  `src/lib/validate.ts`, схема БД). Иначе backend и frontend разойдутся в форме данных.
- **Все вопросы владельцу задаются до делегирования.** Субагенты спросить вас не
  могут — если им не хватает решения, они возвращают вопрос ведущему.
- **Зоны не пересекаются**, поэтому два разработчика правят одну рабочую копию без
  конфликтов.

В конвейере GitHub Actions этап разработки пока идёт одним агентом, без субагентов.

Вызвать субагента вне `/task` можно напрямую: «пусть reviewer посмотрит ветку» или
`@agent-reviewer`.

## Работа через Linear

Linear — витрина, GitHub — исполнитель. Двусторонний GitHub Issues Sync зеркалит
задачу, метки, статус и комментарии в обе стороны, поэтому агентам всё равно, где
вы нажали кнопку.

| Вы в Linear | Что происходит |
| --- | --- |
| Создали задачу в команде Crypto Development, поставили метку `agent:plan` | в GitHub появляется issue с меткой → агент пишет план, он приходит комментарием в Linear |
| Ответили комментарием на «Вопросы по задаче» | планирование перезапускается само, приходит план |
| Поставили метку `agent:build` | агент открывает PR; ссылка на него появляется в задаче |
| Комментарий `@claude поправь …` в задаче | агент дорабатывает |
| Смержили PR в GitHub | issue закрывается, задача в Linear переходит в Done |

Мерж остаётся в GitHub: там дифф, CI и ревью.

### Настройка Linear (один раз)

1. Linear → Settings → Integrations → **GitHub**: подключить аккаунт `vleukhin`,
   дать доступ к репозиторию `depo`. В Settings → Connected accounts привязать
   свой личный GitHub.
2. В настройках интеграции GitHub → **GitHub Issues Sync** → «+» → репозиторий
   `vleukhin/depo` ↔ команда Crypto Development, режим **two-way**.
3. К одной команде можно привязать несколько репозиториев, но по документации
   Linear двусторонним одновременно бывает только один. Проверьте направление у
   привязки `depo` в списке: задача, созданная в Linear, должна попадать в GitHub.
4. Создать метки `agent:plan`, `agent:questions` и `agent:build` — имена должны
   совпадать с метками в GitHub буква в букву.

### Что проверить на первой задаче

Это поведение sync в документации Linear описано не до конца, поэтому первая
задача — проверочная:

- **От чьего имени Linear действует в GitHub.** Воркфлоу принимают события от
  владельца репозитория и от `linear[bot]`. Если этап не стартовал (job в Actions
  помечен skipped), посмотрите в событии, кто указан как sender, и поправьте имя
  в условии `if:` и в `allowed_bots` трёх воркфлоу `agent-*.yml`.
- **Доезжает ли метка**, поставленная в Linear, до GitHub issue. Если нет —
  ставьте метку в GitHub или переводите запуск на статус задачи.
- **Доезжает ли комментарий с планом** от агента обратно в Linear.

Кто может запускать агентов: все участники вашего рабочего пространства Linear с
доступом к команде Crypto Development. Пока вы там один — это только вы. Репозиторий публичный,
и чужие GitHub-issues тоже попадут в Linear: читайте задачу, прежде чем ставить
на неё метку.

## Разовая настройка GitHub (делаете вы, ~10 минут)

1. **Установить приложение Claude** на репозиторий: https://github.com/apps/claude →
   Install → только `vleukhin/depo`.
2. **Добавить один секрет** в Settings → Secrets and variables → Actions:
   - `CLAUDE_CODE_OAUTH_TOKEN` — если работаете по подписке Claude (Pro/Max):
     выполните локально `claude setup-token` и вставьте результат; **или**
   - `ANTHROPIC_API_KEY` — ключ из console.anthropic.com (оплата по токенам).
3. **Создать метки** `agent:plan`, `agent:questions` и `agent:build` (Issues → Labels), если их ещё нет.
4. **Защитить `master`**: Settings → Branches → Add rule → Require a pull request
   before merging + Require status checks (`check`). Тогда в прод ничего не попадёт
   мимо PR и зелёного CI.
5. **Развести окружения Vercel — до первой задачи.** См. следующий раздел.

## Preview-деплои и боевые секреты

По `DEPLOY.md` переменные окружения заданы со scope **Production + Preview**. Значит,
код из ветки агента разворачивается в preview с боевой базой Turso и ключом Bitget с
правом вывода — ещё до того, как вы его посмотрели. Для конвейера это нужно исправить:

- в Vercel → Settings → Environment Variables оставьте боевые значения только для
  **Production**;
- для **Preview** задайте отдельные: свою `APP_PASSWORD`/`AUTH_SECRET`, отдельную
  базу Turso (`turso db create depo-preview`, можно с копией данных) и **не задавайте**
  `BITGET_*`, `KUCOIN_*`, `TRONRENTAL_API_KEY`, `EXCHANGE_PROXY_*`, `TELEGRAM_*`,
  `CRON_SECRET`, `EXTERNAL_API_TOKEN`.

Preview при этом остаётся рабочим стендом для ручной проверки интерфейса, но
ошибка в коде агента не дотянется ни до денег, ни до боевых данных.

## Что агентам запрещено

Полный список — в `.claude/pipeline/build.md`. Главное: не мержить и не пушить в
`master`, не ставить npm-пакеты, не трогать `.github/` и `.claude/`, не обращаться к
проду, базе и биржам. В секретах GitHub Actions лежит только токен Claude — боевых
ключей у агентов нет физически.

## Стоимость и лимиты

Каждый этап — отдельный запуск с лимитом ходов (`--max-turns`) и таймаутом в
воркфлоу. По подписке запуски расходуют её лимиты, по API-ключу — оплачиваются по
токенам. Модель не закреплена (берётся модель по умолчанию у action); закрепить можно
флагом `--model` в `claude_args`.

## Перенос на другие проекты

Скопируйте `.github/workflows/agent-*.yml`, `.github/ISSUE_TEMPLATE/`, каталог
`.claude/pipeline/` и напишите свои `CLAUDE.md` и `docs/RUNBOOK.md`. В воркфлоу
меняются только команды проверок (`npm run …`) и список `--allowedTools`; в
`.claude/pipeline/*.md` — разделы про рискованные зоны проекта.
